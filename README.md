# VedaAI — AI Assessment Creator

A full-stack web app that lets a teacher describe an assignment and receive a structured, well-formatted question paper generated by an LLM. Built for the VedaAI hiring assignment.

The app covers the full pipeline: a Next.js form captures the teacher's intent, an Express API enqueues a background job in BullMQ, a worker calls the OpenAI API, stores a validated/structured paper in MongoDB, and pushes a real-time update over WebSocket so the frontend can render the paper as soon as it's ready. The output page renders the paper as an exam-style document with student-info fields, sectioned questions, difficulty badges, and one-click PDF export.

### Request lifecycle

1. Teacher fills the form on `/` and submits. Validation runs client-side (Zod-style rules) and server-side (Zod schema in the route).
2. `POST /api/assignments` creates the `Assignment` document with `status: "pending"`, extracts text from any uploaded PDF/TXT, and enqueues a `paper-generation` job in BullMQ. The job ID is `assignment:<id>` so we can reverse-map events.
3. The API responds with `{ id, status }`. The frontend navigates to `/assignment/[id]` and the page server-fetches the initial record (which is `pending`).
4. The page mounts `AssignmentView`, which:
   - Opens a Socket.io connection and subscribes to room `assignment:<id>`.
   - Polls every 4 s as a fallback in case the socket misses an event.
5. The **worker** picks the job up, sets `status: "processing"`, builds a structured prompt (`utils/prompt.ts`), calls OpenAI in JSON mode, validates the response with Zod, and saves the paper. BullMQ's built-in pub/sub fires `active` and `completed` events on Redis; the API server subscribes via `QueueEvents` and emits `assignment:update` to the correct socket room.
6. Frontend receives the event, refetches the full assignment, and renders `QuestionPaper`.
7. The teacher can hit **Regenerate** (re-enqueues a fresh job) or **Download PDF** (client-side `html2canvas` + `jsPDF`).

### Why not render the raw LLM response?
- The model is asked to return strict JSON (no markdown, no prose) via OpenAI's `response_format: json_object`.
- The response is parsed and validated with a Zod schema (`PaperSchema` in [backend/src/services/llm.ts](backend/src/services/llm.ts)). Any deviation throws and the job goes to `failed`.
- Question numbering is re-stamped server-side so the UI can trust it.
- The frontend never renders LLM text outside the validated `Question.text` field.

### Why BullMQ + WebSockets?
- LLM calls take 10–30 s. Keeping them off the request thread lets the API stay snappy and lets us retry/scale workers independently.
- Using BullMQ's `QueueEvents` (Redis pub/sub under the hood) means the API server learns about job state changes from the worker process automatically — no extra channel to wire up. The API then forwards to Socket.io rooms.
- Polling is kept as a 4 s fallback so a dropped WS connection never strands the UI.

### Caching
- After a job completes, the assignment document is cached in Redis (`assignment:<id>`, TTL 1 h). `GET /api/assignments/:id` checks the cache first; the cache is invalidated on regenerate.

## Setup

### 0. Start MongoDB & Redis

```bash
# From the project root
docker-compose up -d
```

This starts:
- **MongoDB** on `mongodb://localhost:27017`
- **Redis** on `127.0.0.1:6379`

(If you prefer local installs without Docker, ensure MongoDB and Redis are running on their default ports before starting the backend.)

### 1. Backend

```bash
cd backend
cp .env.example .env        # fill in GROQ_API_KEY
npm install
```

The default `.env` works for local Mongo + Redis. Edit `GROQ_API_KEY`. Optionally change `GROQ_MODEL`.

Run the API server and the worker in **two terminals**:

```bash
# Terminal 1 — API + WebSocket server
npm run dev

# Terminal 2 — background worker
npm run dev:worker
```

API will be live at `http://localhost:4000`. Health check: `GET /health`.

### 2. Frontend

```bash
cd frontend
cp .env.example .env.local   # defaults point at http://localhost:4000
npm install
npm run dev
```

App is at `http://localhost:3000`.

## Deploying to Vercel + Render

### Frontend on Vercel

- Import the `frontend/` folder as a Vercel project.
- Framework preset: Next.js.
- Build command: `npm install && npm run build`
- Output is handled automatically by Vercel.

Set these environment variables in Vercel:

- `NEXT_PUBLIC_API_URL=https://your-render-backend.onrender.com`
- `NEXT_PUBLIC_WS_URL=https://your-render-backend.onrender.com`
- `NEXT_PUBLIC_GOOGLE_CLIENT_ID` if you use Google sign-in

### Backend on Render

- Create a Node web service from the `backend/` folder.
- Build command: `npm install && npm run build`
- Start command: `npm run start`
- Add a second Render worker service from the same `backend/` folder.
- Worker start command: `npm run start:worker`

Set these environment variables in Render:

- `PORT=4000` or the port Render assigns
- `NODE_ENV=production`
- `CLIENT_ORIGIN=https://your-vercel-frontend.vercel.app`
- `MONGO_URI` from MongoDB Atlas
- `REDIS_HOST` and `REDIS_PORT` from your Redis provider
- `GROQ_API_KEY` from the Groq dashboard
- `GROQ_MODEL` if you want to override the default model
- `JWT_SECRET` as a long random string
- `JWT_EXPIRES` if you want a custom token lifetime
- `GOOGLE_CLIENT_ID` if you use Google sign-in

For `MONGO_URI`, create a cluster in MongoDB Atlas and copy the connection string.
For Redis, use a hosted Redis provider that gives you a standard TCP host and port.

## API reference

| Method | Path                                | Body                                                                                                                                              | Returns                          |
| ------ | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| POST   | `/api/assignments`                  | `multipart/form-data`: `title`, `subject?`, `gradeLevel?`, `dueDate`, `questionTypes` (JSON string), `additionalInstructions?`, `file?` (pdf/txt) | `{ id, status }`                 |
| GET    | `/api/assignments/:id`              | —                                                                                                                                                 | Full assignment doc              |
| POST   | `/api/assignments/:id/regenerate`   | —                                                                                                                                                 | `{ id, status }`                 |
| GET    | `/api/assignments`                  | —                                                                                                                                                 | Recent 50 assignments (summary)  |

WebSocket events on the `/` namespace:

- Client → `subscribe`(assignmentId) / `unsubscribe`(assignmentId)
- Server → `assignment:update` with:
  - `{ type: "status", status: "processing" }`
  - `{ type: "completed", assignmentId }`
  - `{ type: "failed", assignmentId, error }`

## Approach notes

- **Validation lives in two places by design.** The frontend prevents obvious mistakes (empty title, past due date, negative counts) so the user gets instant feedback. The backend re-validates the same fields with Zod so the API never trusts the client. Schema for the LLM response is also Zod-checked so a malformed model reply is caught before it reaches Mongo.
- **Prompt structuring.** `utils/prompt.ts` converts the form into (a) a strict system prompt that pins the JSON format and (b) a user prompt that lays out the composition, total marks, optional source material, and a default difficulty distribution. Marks are summed and the model is told the exact target so the output adds up.
- **Sections are derived, not user-entered.** The model groups questions into logical sections (typically by question type, falling back to difficulty), gives each a title + instruction, and numbers questions sequentially. The backend re-stamps numbers as a safety net.
- **PDF export prioritises fidelity over print-CSS.** The output uses `html2canvas` to rasterise the rendered paper then composes it into a paginated A4 PDF with `jsPDF`. This avoids the well-known issues with browser "Print to PDF" (broken page breaks, missing background colours, weird font rendering).
- **Difficulty is visualised.** Each question gets a colour-coded pill (green/amber/rose for easy/moderate/hard) that survives the PDF export.
